Overview

PlugSec connects security tools with a config file instead of code. You describe a tool once; one engine handles login, paging, retries and mapping, and every record lands in one common format.

What you get

  • Config, not code. A new tool is a YAML file in configs/integrations/ or the Add integration wizard. It goes live without a restart.
  • One common schema. Users, devices and events from every tool sit in the same tables, each row tagged with its source and fetched_at.
  • Reliable by default. The same retry, rate-limit and quarantine rules apply to every connection.
  • Safe secrets. Configs hold names like ${github_token}; values live in .env and an encrypted vault.
  • Visible health. Each connection shows its status, last run, records and errors, with alerts on repeated failure.

Quick start

You need Python 3.11 or newer, on Windows or macOS.

1. Install and run

python -m venv .venv
.venv\Scripts\activate          # macOS / Linux: source .venv/bin/activate
pip install -r requirements.txt
python run_all.py

On the first run, run_all.py:

  • creates .env from .env.example,
  • generates SECRETS_KEY, the master key of the encrypted vault,
  • creates three sign-ins (admin, analyst, viewer) and prints their passwords once. Only hashes are saved.

2. Add your API keys

Fill in the keys for the tools you use in .env. A connection without its keys shows Not configured and never runs.

github_token=     GITHUB_OWNER=     GITHUB_REPO=
okta_token=       OKTA_DOMAIN=integrator-1234567.okta.com
jira_email=       jira_token=       JIRA_DOMAIN=yourteam.atlassian.net
nvd_api_key=      # optional

3. Sign in and see data

  1. Open http://localhost:8000 and sign in with one of the printed accounts.
  2. Overview shows connection health and the last 24 hours.
  3. Integrations lists every connection; Run now pulls data immediately (analyst or admin).
  4. Events, Users and Devices show the records in the common format. Click a row for every field and the raw JSON.

Forgot a password? python -m integration_platform.auth set-password admin admin sets a new one; restart the platform afterwards.

Add an integration

Admins add a tool from Add integration in the sidebar, or by dropping a YAML file into configs/integrations/ (picked up within 5 seconds).

The wizard, step by step

  1. Basics: display name, integration ID, base URL and schedule.
  2. Auth: pick the login type and reference secrets by name.
  3. Request: the endpoint path, method and query parameters.
  4. Pagination: how the API splits results across pages.
  5. Mapping: fetch a sample response; the assistant suggests which tool field fills which common field. Code checks every path against the sample, and you approve or edit it.
  6. Test: runs the config once against the real API, without saving, and shows the first records raw and normalised.
  7. Save: writes the YAML file and schedules it right away.

A live YAML panel stays in sync with the form; you can edit either side.

Example: CISA KEV

The CISA Known Exploited Vulnerabilities feed is public JSON: no login, no paging.

name: cisa_kev
display_name: "CISA KEV"
enabled: true
base_url: "https://www.cisa.gov"
auth: { type: none }
schedule_seconds: 900
streams:
  - name: kev
    entity: event
    endpoint: "/sites/default/files/feeds/known_exploited_vulnerabilities.json"
    records_path: "vulnerabilities"
    timeout_seconds: 60
    mapping:
      id: "cveID"
      type: "'vulnerability'"
      timestamp: "dateAdded"
      description: "vulnerabilityName"
    transforms: { default_severity: high, time_format: iso8601 }

Streams (endpoints)

One integration holds one or more streams. Each stream is one endpoint: it shares the integration's base URL, login, headers, retries and rate limits, and has its own path, paging, mapping and table. In the wizard, the Endpoints step adds, duplicates and removes them; the Mapping and Test steps have one tab per endpoint.

for_each: one call per parent record

Some data needs one call per item: languages per repository, details per alert ID. for_each runs a stream once for every record of another stream of the same integration. It is a generic engine feature; GitHub uses it through config only.

streams:
  - name: repositories                  # the parent: always runs first
    entity: repository
    path: /user/repos
    pagination: { type: link }
    mapping: { id: id, full_name: full_name, description: description }
  - name: dependabot_alerts
    entity: event
    for_each:
      stream: repositories              # parent stream
      as: repo                          # name of the parent record in templates
      concurrency: 4                    # parallel requests (default 4, max 16)
      where: "!archived"                # optional JMESPath filter on the parent record
      skip_status: [403, 404]           # per-item errors that are recorded and skipped (default)
    path: "/repos/{{ repo.full_name }}/dependabot/alerts"
    parent_status:
      field: dependabot_status
      ok: enabled
      by_reason: { "not accessible": no access }   # text in the API's error message, checked first
      by_status: { 403: disabled, 404: no access }
    mapping:
      id: "join('#', [parent().full_name, to_string(number)])"
      resource: "parent().full_name"
      severity: security_advisory.severity
      timestamp: updated_at
  • Order: a parent stream always runs before its for_each streams, whatever the order in the file. Cycles are rejected when the config is saved.
  • Concurrency and limits: at most concurrency requests at a time. Retries (1 s, 2 s, 4 s), Retry-After and the proactive rate-limit slow-down apply to every item, and a 429 pauses the parallel requests too.
  • Per-item failures: a 403/404 on one item is recorded with the API's reason and skipped; the stream continues. Health shows "N items skipped" with the reasons. A 401, an exhausted rate limit or a network failure stops the stream, as for any stream.
  • Safe templates: the path and params may use only {{ as.field }} (the parent record): no settings, no other data. Values are URL-encoded, ../ is refused, and a parent value can never expand into a ${SECRET}. Settings (${NAME}) are resolved before parent values are filled in.
  • URLs: the base URL and the path are joined with exactly one / (a trailing slash on the base URL or a doubled slash in the path is removed).
  • Test runs use the first 3 parent records; Fetch sample uses the first one.
  • Guard: adding or removing endpoints changes a connector's normal volume, so the exfiltration guard re-learns its baseline when the list of streams changes.

Mapping and transforms

mapping:
  id: uuid                                   # plain path
  user: actor.alternateId                    # nested value
  name: "join(' ', [profile.firstName || '', profile.lastName || ''])"   # combine fields
  type: "'vulnerability'"                    # constant
transforms:
  severity_map: { DEBUG: info, INFO: info, WARN: medium, ERROR: high }
  default_severity: info                     # when the value is missing or unknown
  time_format: iso8601                       # iso8601 | epoch_s | epoch_ms

Times are always stored as ISO 8601 in UTC. Severities are always one of info, low, medium, high, critical.

Reliability

These rules are the same for every connection; no config needed.

Retries

  • Timeouts, network errors and 5xx: retry after exactly 1 s, 2 s and 4 s. If all fail, the run is marked failed with a clear error.
  • 401 and 403: never retried. Health shows Auth failed, because retrying a wrong key cannot help.

Rate limits (HTTP 429)

  1. Wait as long as Retry-After says (seconds or an HTTP date).
  2. Without it, wait for the configured reset header (GitHub x-ratelimit-reset, Okta x-rate-limit-reset).
  3. Without that, back off exponentially.

If an API answers Retry-After: 0 (NVD does), the engine waits the API's known window (fallback_wait_seconds) instead of hammering it. When the remaining-requests header is near zero, the next call waits for the reset first, and min_interval_seconds paces APIs that ask for it. Every wait is logged, e.g. "waited 5s due to Retry-After".

Bad records

A record with a missing required field, the wrong type or an unreadable time is quarantined with its reason. The rest of the run is stored, and the card shows "N records quarantined · View".

Alerts on repeated failure

After 3 failed runs in a row (alert_after_failures), PlugSec sends one alert for that streak to Slack (SLACK_WEBHOOK_URL) and email if configured, and a "recovered" message once it works again. The dashboard banner and the log always get it.

Security

Secrets by name only

Configs hold a name such as ${github_token}, never the value. A pasted secret is rejected when the config is saved.

Encrypted vault

On first use, each referenced secret is copied from .env into the vault, encrypted with SECRETS_KEY (Fernet). No API ever returns a secret value.

Log masking

Every log line and stored error passes a filter that masks known secret values, bearer / basic / SSWS headers, JWTs, AWS keys and key=value secrets.

Git hygiene

.env, the database (with the vault) and the logs are git-ignored. A test scans committed files and logs for real secret values.

Rotate and revoke

Health shows Rotate secret when a secret is older than secret_max_age_days. Revoke (admin) disables the connection and wipes its secrets; a tombstone stops .env from bringing them back.

Token abuse detection

Each connection learns how many records a normal run pulls (the median of its last 10 good runs). A run that pulls more than 5 times that, and at least 50 records, pauses the connection, raises a critical alert and opens a ticket. If the jump is expected, for example a first full scan, an admin clicks Resume and the baseline is re-learnt from then on.

Why it matters: in August 2025, attackers used OAuth tokens stolen from the Salesloft Drift chat integration to export large amounts of data from hundreds of organisations' Salesforce instances. The tokens were valid, so logins looked normal; the unusual signal was the volume of data leaving. That is the pattern this check watches for.

Roles and the audit log

Every page and API needs a session; the server checks the role on every request. The audit log records sign-ins, failed sign-ins, denied requests and every change, with user, role, target and outcome. After 5 failed sign-ins, that username is locked for 30 seconds from that address.

Session login

For APIs that hand out a token from a login call. Example (Lacework FortiCNAPP):

auth:
  type: session_login
  login_url: /api/v2/access/tokens        # called once; the token is reused until ttl_seconds
  headers: { X-LW-UAKS: "${lacework_secret}" }
  body: { keyId: "${LACEWORK_KEY_ID}", expiryTime: 3600 }
  token_path: token                       # or token_response_header: X-auth-access-token
  header: Authorization
  prefix: "Bearer "
  ttl_seconds: 3300

A 401 on a data call triggers one fresh login. The token is masked in logs like every other secret.

FAQ

What if an API is unusual?

Most APIs fit the config options. For the rare case that does not, an admin can add a small plugin: a class with process(records, config) that runs on the raw records before mapping, referenced as custom_step.

custom_step: "integration_platform.plugins.example_step.KevSeverity"

Where is data stored?

In one SQLite file, data/platform.db. The tables users, devices and events hold the common schema; others hold runs, quarantined records, sync state, the encrypted secrets, actions and the audit log.

Does AI change data?

No. The assistant only suggests a mapping from a sample. Code checks every suggested path against the sample and drops the ones that do not exist, and an admin reviews and applies it. Secrets and personal data are masked before anything is sent. Without an AI key, a rule-based mapper does the same job offline.

Does it need the internet?

Only to reach the tools you connect. The dashboard and docs load no external scripts or fonts.
